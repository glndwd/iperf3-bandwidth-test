## 专线带宽测试，要测的其实是四个数

只看下载速度是不够的，一次像样的专线验收至少覆盖四个指标：带宽、丢包率、抖动，以及包转发率（pps）。

| 指标 | 说明 | 推荐工具 |
| --- | --- | --- |
| 带宽 | 单位时间内能传输的最大数据量 | iPerf3 |
| 丢包率 | 打流时丢失报文占总报文的比例 | iPerf3（UDP 模式） |
| 抖动（Jitter） | 延迟的波动幅度 | iPerf3（UDP 模式） |
| 包转发率（pps） | 每秒转发的报文数，反映小包处理能力 | Netperf 或 iPerf3 小包模式 |

不同业务看的重点不一样。跑视频会议、跨境直播，丢包率和抖动比峰值带宽更要命，丢 1% 就够画面卡成幻灯片；跑数据库同步、接口调用这类小包密集的业务，pps 才是瓶颈。只测一个下载速度，等于只做了四分之一的体检。

## 测试环境：专线两端各一台机器就能起步

最低配置是专线两端各一台装好 iPerf3 的服务器，一端做服务端、一端做客户端；要验证大带宽，客户端一侧再多备几台机器，或者多开几个进程。前提是专线的接入和路由已经配通，不然测的是排障，不是带宽。

以 CentOS 为例，安装就两行命令：

bash
yum install iperf3
iperf3 -v    # 回显版本号即安装成功


iPerf3 支持 Linux、Windows、macOS，开源免费，也是目前企业专线、云专线验收的行业标准工具。两个容易忽略的准备细节：

- 测试机和陪练机尽量用相同配置。一强一弱的结果会落在弱的那台上，你以为是线路问题，其实是机器瓶颈。
- 线路带宽几百兆以上时，先在设备上开网卡多队列，否则单核 CPU 会先被打满。以 eth0 为例，执行 `ethtool -L eth0 combined 4`，再把中断分摊到各个队列上。

## iPerf3 实测：服务端和客户端命令照抄即可

一端以服务端模式监听，另一端连上去打流，默认走 TCP，加 `-u` 改 UDP。iPerf3 是 C/S 架构，理解了这一点，命令就不用死记。

常用参数先过一遍：

| 参数 | 作用 |
| --- | --- |
| -s / -c | 服务端监听 / 客户端连接 |
| -p | 端口，默认 5201 |
| -t | 测试总时长，默认 10 秒 |
| -u | 改用 UDP 发包 |
| -l | 读写缓冲长度，测带宽设 1400，测 pps 设 16 |
| -b | UDP 模式的目标带宽，比如 100m |
| -P | 并发连接数 |
| -A | 绑定 CPU 亲和性，避免进程跨核调度 |
| -R | 反向传输，用来测上行 |

TCP 测带宽：

bash
# 服务端
iperf3 -s -i 1
# 客户端：4 条并发流，跑 60 秒
iperf3 -c <对端IP> -t 60 -P 4


UDP 测丢包和抖动：

bash
iperf3 -u -l 1400 -b 100m -t 120 -c <对端IP> -i 1


这里有个关键细节：高带宽线路上，单条 TCP 流经常跑不满，卡在几百兆上不去。这不是线路缩水，多数时候是单流受 TCP 窗口和单核处理能力的限制。华为云验收专线时，是在 6 台云服务器上各起一个 iPerf3 进程、指定 6 个不同端口同时打流，每条压 100M，合计 600M。你手头机器不够，用 `-P 4` 开并发、或多开几个端口跑多进程，思路相同。

顺带提醒：iPerf3 和 iPerf2 互不兼容，两端必须用同一个大版本，连不上先查版本。

### 测试结果怎么读

UDP 模式跑完，输出长这样：


[ ID]  Interval        Transfer    Bandwidth      Jitter    Lost/Total Datagrams
[  4]  0.00-10.00 sec  237 MBytes  199 Mbits/sec  0.027 ms  500/30352 (1.6%)


| 字段 | 含义 |
| --- | --- |
| Transfer | 传输的总数据量 |
| Bandwidth | 带宽大小 |
| Jitter | 抖动 |
| Lost/Total Datagrams | 丢失报文数 / 总报文数，即丢包率 |

多流测试看最后的 SUM 行，那是所有流加起来的总和。UDP 模式下 Bandwidth 是你用 `-b` 指定的发包速率，真正要盯的是丢包率和抖动这两个数。想顺手算 pps 也不难：对端收到的包数除以测试时间。

## 进阶：用 Netperf 测包转发性能

pps 用小包打流来测。iPerf3 把 `-l` 调到 16 就能凑合测，要更细的数据就用 Netperf 的 UDP_STREAM。它装完自带两个工具：netserver 做服务端，netperf 做客户端。

bash
# 服务端
netserver -p 11256
# 客户端：-m 1 测 pps，-m 1400 测带宽
netperf -H <对端IP> -p 11256 -t UDP_STREAM -l 300 -- -m 1


pps 的算法是发送成功的报文数除以测试时间。包转发性能非常吃 CPU，阿里云测自家专线时用了 8 台实例并发压测，你要测高 pps，同样得靠多台机器或多实例堆上去。

## 延迟、丢包和稳定性：ping、mtr、speedtest 各管一段

延迟和丢包用 ping、mtr，公网出口速率用 speedtest-cli，长期观察链路利用率用 nload 或 iftop，各管一段，别指望一个工具全包。

- 持续 ping：`ping -c 100 -i 1 对端IP`，看返回时间的波动，波动大说明线路不稳。
- mtr 比 traceroute 直观：`mtr -r -c 50 对端IP` 会逐跳列出每一跳的延迟和丢包，能看出问题出在本地、运营商骨干还是对端机房。
- speedtest-cli 测公网出口基准：下载速率达到签约带宽的 90% 以上算正常，上下浮动 ±10Mbps 都在合理范围。它测的是单线程峰值，数值偏低先别急着下结论。
- 大文件上传下载跑一段时间，观察有没有断流和速率跳水，这类稳定性问题打流工具不一定暴露。

定位瓶颈的思路是分层：先在终端直连跑 speedtest 确认出口带宽，再逐段往内网测，网关转发、交换机到终端、跨网段端到端，哪一段掉得厉害，瓶颈就在哪一段。

## 测出来的带宽偏低？先排查这五处

带宽测不到标称值，多数情况是测法或本机配置的问题，按下面的顺序排查完，再考虑找服务商：

1. 单流跑不满：加 `-P` 开并发，或多端口多进程同时打。
2. CPU 单核打满：用 `-A` 把 iPerf3 绑到指定核，配合网卡多队列。
3. MTU 不匹配：UDP 模式下 `-l` 用 1400，避开 IP 分片；分片一旦丢失会全算进丢包率，数据看着很难看。
4. 网卡协商速率和 QoS 限速：检查网卡有没有协商在百兆半双工，路由器上有没有对特定端口或时段做 QoS 限速，打流时容易撞上。
5. 测试时间太短：10 秒的结果波动很大，验收级测试至少跑 120 秒，腾讯云的文档直接建议 300 秒。

全部排查完还是低，再拿数据找服务商。工单里附上完整命令和 SUM 行的输出，比一句“网速慢”管用得多。

## 常见问题

**专线带宽测试要跑多久才准？**
至少 120 秒。时间越长结果越稳，10 秒的短测受 TCP 慢启动影响，数值普遍偏低。

**speedtest 和 iPerf3 哪个准？**
测的对象不同，谈不上谁更准。speedtest 测的是你到公网测速点的单线程速率，受测速点位置影响大；iPerf3 测的是专线两端之间的真实吞吐，验收线路用它。

**UDP 打流带宽上不去，是不是线路有问题？**
不一定。UDP 的发包速率由 `-b` 参数决定，它只管按这个速率发。反映线路质量的是丢包率和抖动：丢包长期在 1% 以上，说明这条线路吃不下这个速率；把 `-b` 往下调，找到丢包趋近于 0 的临界点，那才是线路的真实水位。
